Minus twenty minutes
of not knowing.

An alert tells you what broke. It never tells you why. The twenty minutes that follow, at 03:00, go into assembling context by hand and guessing. Minus20 takes those minutes off every Kubernetes incident: a falsifiable root-cause hypothesis, with its evidence, in your chat about a minute after the alert. Inside your cluster. The logs never leave.

The 03:00 problem

The page says KubePodCrashLooping. What you actually need is in five places: the pod's events, its previous container's log, the metrics around the restart, what was deployed in the last hour, and what happened last time. Gathering that by hand takes ten to thirty minutes, and it is the same ten to thirty minutes every time. That is the number an engineering manager is paying for, in sleep and in MTTR.

How it works

Alertmanager ──webhook──► ingest-api ──► Redis Stream ──► analyzer-worker │ collectors: K8s events · pod logs · Prometheus · Loki · CloudWatch │ REDACTION (mandatory: secrets, tokens, e-mails, IPs) │ dedup · storm grouping · correlation · daily budget │ ONE model call, hard timeout ──► Postgres (audit trail) ──► Slack / Telegram Engineer in Telegram ──► agent: read-only tools · memory of verdicts (pgvector) · /report Any agent CLI ──► the same tools over MCP

Two always-on processes inside your cluster. The reflex is a deterministic pipeline: one bounded model call per alert, and the raw alert is delivered even when the model is down, over budget, or wrong. The agent answers follow-up questions with a closed set of read-only tools and remembers the engineer's verdicts. Neither holds a tool that can change anything.

Three decisions worth defending

Pipeline, not an agent loop, on the alert path

One call, one hypothesis, a hard timeout, a daily budget. Predictable cost (about $0.001 per alert on a cheap cloud model, $0 locally) and an audit trail of exactly what the model saw.

It recommends. It never acts.

Read-only credentials. No write tools. Output is text, never executed. The moment an on-call bot can act, every false positive becomes an incident of its own.

Privacy first

Redaction runs before any model call and has no off switch. With a local model nothing leaves the cluster. Which model is a config value; the code never changes.

Fastest way to see it

One Helm install with the demo switch on: it breaks a pod inside the release namespace under its own write-capable service account, pages itself, and the first real hypothesis is in your chat a few minutes later. The product's service account stays read-only.

kubectl create namespace minus20
kubectl -n minus20 create secret generic m20-telegram --from-literal=bot-token='<token>'
helm install m20 oci://ghcr.io/maxuver/charts/minus20 -n minus20 \
  --set config.notifier=telegram --set config.telegramChatId=<your chat id> \
  --set config.llmProvider=ollama --set config.ollamaUrl=http://<ollama>:11434 \
  --set demo.chaos.enabled=true

No Ollama? Any OpenAI-compatible key works (Mistral, DeepSeek, Gemini): --set config.llmProvider=openai --set config.openaiBaseUrl=.... Images are signed (SLSA provenance, verify with gh attestation verify), scanned, and ship an SBOM.
